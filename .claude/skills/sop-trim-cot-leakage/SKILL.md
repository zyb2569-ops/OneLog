# sop-trim-cot-leakage

被动写作纪律：说明性文字对现在的代码负责，不对当时那次会话负责。边写边守。不要等用户点名。

说明性文字：规范、设计说明、README、注释、JSDoc、Skill 正文。不含 PRD（走 `doc-voice`）、聊天记录、提交说明。

## 边写边守

当场按规则落笔。不出审计表，不另起一遍 pass，不强制 subagent。改已有文字只动这次碰到的段落，不要顺手扫全文件或全仓。

用户说简化时不要跑本 Skill（走 `sop-find-simplifications`）。只提交时不要跑。

## 一条检验

对每个将写下或将改到的句子问：**HEAD 上的读者，看不到任何会话记录、PR 讨论、未提交草稿，能不能解析每处指称、核对每个断言？** 不能：先数清完整命题（谁、条件、必须/可以/禁止、失败会怎样），把还成立的事实改写成现在时，删掉会话痕迹。句子里没有任何命题：整句删。

## 交接

删这段文字会改变承诺行为、公开接口或上下游时：**停手，不要改。** 告诉用户这是简化候选，等用户主动说简化再走 `sop-find-simplifications`。本 Skill 不因为发现候选就去扫代码表面。

## Taxonomy

1. **死掉的设计会话引用** — `(decision 7)`、`(audit C2)`、`design §4.7`、`plan §1.4`、阶段号（`T4`、`W3`、`P-I`）、「设计稿 §」。有已提交的主人就改成名字和路径；没有就把事实写成能单独成立的句子，删掉引用。
2. **PR / 分支视角** — 「这次 PR 加了」「本分支」「后面那个 PR」「上一笔 commit」。写成已提交的机制或扩展点；未做的工作写成 `TODO` 或 issue。
3. **变更叙事和版本戳** — 「以前是」「不再」「旧的 X」、对着过去说话的「现在」「本版」「this cut」。写成现在的行为。修过的回归写成现在时反事实（「没有 X 就会 Y」），不要写成仓库史。
4. **评审场面** — 「评审否决了」「评审确认了」、草稿第几版。留下决策和理由当事实；删掉是谁在哪一轮说的。
5. **说给评审听的辩护** — 「这个转换是安全的，只是…」「这是对的，因为…」。写成维护者不能破坏的不变量；代码已经能看出来就删注释。
6. **走读和推导** — 「先做 X 再做 Y」、把测试步骤再讲一遍、对显而易见分支的证明。删。只留代码表达不了的契约或不变量。
7. **含糊和计划残渣** — 「暂时应该够了」「大概没问题」、没有标记的推迟。升成 `TODO`/`FIXME`，或写成真实边界；删掉含糊。
8. **写作语言串台** — 正文是中文却夹着未翻译的工作草稿分隔，或反过来。翻译或删。

校准见 [examples.md](references/examples.md)。改已有段落时可用 [recall-batteries.md](references/recall-batteries.md) 做探针，命中仍要语义判断；电池不是定义。

## 不是泄漏

- **Issue 引用** — `#1470`、`TODO(name):` 在 HEAD 能解析，可留。
- **抑制/忽略的理由** — linter disable、空 catch 的原因是必留正文；理由写错了就改理由，不要整段删。
- **现在时反事实** — 「没有 X 就会 Y」。
- **测过的边界** — 「（实测：…）」里的「实测」是出处，要留。
- **运行时的旧/新** — 「旧连接排空后新连接才接」说的是活对象交接，不是仓库史。
- **仓外能解析的引用** — RFC 章节、Figma 画板名。`§` 禁的是未提交的内部草稿，不是外部标准。
- **讲 PR 流程的文档** — 「PR 正文应写…」在谈流程；禁的是某篇说明采用「这一次 PR」的视角谈代码。

## 改之前

先列出这段里的命题，再改。不要把义务改成认可、把假想写成已交付、连真事实一起删、或去掉数字的出处。见 [examples.md](references/examples.md) 的过纠。
