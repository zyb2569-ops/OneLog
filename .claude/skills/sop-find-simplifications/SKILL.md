# sop-find-simplifications

主动审计：用调用方证据列出可以删、折或降级的简化候选。默认只出清单，不改生产行为。

写文档或注释时不要跑本 Skill。平常改功能时不要跑。清理会话泄漏走 `sop-trim-cot-leakage`。

## 步骤

1. **范围。** 用户必须点名路径或模块。没点名就停，问范围，不要猜、不要全仓扫。用户明确说「全仓」才全仓。未提交改动的审查走 `sop-review-diff`。
2. **取证。** 在范围内查每个符号、接口、配置项、事件名的调用方，分成：
   - **生产**：业务运行路径会走到的代码
   - **非生产**：只有测试、文档、注释、快照在用
   - **看不清**：示例、脚本、反射/配置加载。先读调用点再归类，不要只靠名字
3. **只保留强候选。** 有证据表明当前设计成本高于收益，才进清单：
   - 生产侧没有调用方
   - 只有测试或文档在用，且它们钉住的行为不是业务要保留的
   - 两套表示镜像同一件事
   - 每个实现都必须支持、但没有任何调用方的缝
   - 为没有产品负责人的假想场景准备的分支、开关、兼容路径
   - 手写实现了语言/运行时已经提供的能力，换掉能删掉实现和专用测试
   不够格的不要写进清单：一次拼写、凭「看起来复杂」、用户没有授权就去拆有意保留的双实现。
4. **小问题。** 范围很小、不是设计决策：在代码里写短 `TODO`/`FIXME`，不要当成简化候选。
5. **交接。** 候选若是「这段说明文字从会话视角说话，删了不改行为」：告诉用户改走 `sop-trim-cot-leakage`（写这些文字时被动触发），不要在本 Skill 里改字。本 Skill 不因为列过候选就去扫注释。
6. **停。** 把候选交给用户：每条写清位置、建议动作（删 / 折 / 降级）、生产 vs 非生产证据。列完就停。不要接着改、不要 `sop-start-task`、不要把候选写成 Agent Notes。

等人挑了之后，按分档动手：琐碎直接改；普通先 `sop-load-specs`；改业务流程、代码行为或上下游则 `sop-grill-with-docs`。简化改完后若还在写说明性文字，再按被动触发跑 `sop-trim-cot-leakage`。

## 不要

- 不要把审计当成开工
- 不要写 Agent Notes 或另建笔记库
- 不要规定必须用哪种搜索工具或必须上 CodeGraph
- 不要在用户说提交时顺手跑本 Skill
