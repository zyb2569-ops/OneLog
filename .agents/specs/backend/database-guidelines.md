# 数据库规范

> 约束本仓库数据库 DDL、DO 映射、索引与 SQL 的实现契约。

---

## Scenario: 表结构、索引与 SQL 契约

### 1. Scope / Trigger

- Trigger: 修改 `mom/sql/**`、新增或调整 DO/Mapper、补索引、评审 PostgreSQL 设计，或把表接入代码生成时。
- Scope: 适用于本仓库的 MyBatis-Plus + 多数据库脚本维护模式，同时吸收 PostgreSQL 优先设计规则。
- Why: 该流程跨越 SQL 脚本、DO 注解、`BaseDO`、Mapper 查询和部署数据库；若只改其中一层，会出现字段漂移、软删除失效、分页退化或 PG 语义不一致。

### 2. Signatures

- SQL 脚本目录：
  `mom/sql/mysql/`
  `mom/sql/postgresql/`
  `mom/sql/db2/`
  `mom/sql/dm/`
  `mom/sql/oracle/`
  `mom/sql/sqlserver/`
- DO / Mapper 契约：
  `@TableName`
  `@TableId`
  `@KeySequence`
  `@Version`
  `BaseDO`
  `BaseMapperX<DO>`
  `LambdaQueryWrapperX<DO>`
- 常见分页入口：
  `selectPage(reqVO, wrapper)`

### 3. Contracts

#### 3.1 表结构与字段

- 表名、字段名统一使用 `snake_case`。
- 业务表必须有主键、表注释、字段注释。
- 本仓库现有模块默认继承 `BaseDO`，因此物理表通常要与这些字段保持一致：
  `creator`
  `create_time`
  `updater`
  `update_time`
  `deleted`
- PostgreSQL 通用设计建议中的 `is_deleted` 只适用于明确的新建 PG-first 独立表；如果模块已经绑定 `BaseDO.deleted`，禁止只改 SQL 不改 DO/查询封装。
- PostgreSQL 优先类型：
  `bigint + GENERATED AS IDENTITY`
  `boolean`
  `timestamp with time zone`
  `jsonb`
  `text[]/int4[]`
  `ENUM` 或检查约束 + 小表字典
- 大文本使用 `text`，二进制使用 `bytea`；不要套用 `blob/clob` 话术。
- 大表、时序表、明显范围查询表必须评估 `PARTITION BY`。
- 本仓库业务表默认不依赖数据库外键与级联；引用完整性由应用层保证，避免把分布式业务约束锁死在数据库。

#### 3.2 索引

- 高频 `WHERE / JOIN / ORDER BY` 条件必须有索引支撑。
- PostgreSQL 场景优先使用正确索引类型：
  `jsonb` / 数组 -> `GIN`
  范围 / 地理 -> `GiST`
  大体量顺序写入 + 范围扫描 -> `BRIN`
- 禁止重复、冗余、可合并索引。
- 联合索引遵循“等值条件在前、范围条件在后、排序字段跟随查询语义”的原则。
- 禁止把 MySQL 的前缀索引语法照搬到 PostgreSQL 脚本。
- 禁止在索引列上随意包函数；若确实需要，使用表达式索引并同步说明。

#### 3.3 SQL 与查询实现

- 禁止 `SELECT *`。
- Mapper 查询优先写在 `BaseMapperX` 接口 default 方法中，使用 `LambdaQueryWrapperX` 的 `eqIfPresent`、`likeIfPresent`、`betweenIfPresent`。
- 查询默认带软删除条件；如果表使用 `BaseDO.deleted`，查询条件必须对齐 `deleted = false`。
- MPJ 联表查询中，主表和关联表可能存在任意同名列。凡是通过字符串列名表达的主表筛选、排序、`inSql` 条件，都必须统一经过主表列限定方法生成 `t.<column>`；禁止只为当前报错字段维护白名单。
- 大偏移分页禁止长期依赖深 `OFFSET`；大数据量列表优先评估 keyset/seek 分页。
- 事务边界只放在 service 层；Mapper 层不声明事务。
- 批量插入优先多值 `INSERT`；明确是 PostgreSQL 运维/离线装载场景时，可使用 `COPY`。
- 复杂 SQL 可以使用 CTE 提高可读性，但必须结合执行计划确认性能。

#### 3.4 脚本与注解一致性

- 修改表结构时，必须同步对应数据库脚本和 DO 注解：
  `@TableName`
  `@TableId`
  `@KeySequence`
  `@Version`
- 已上线表的演进优先采用幂等 patch：
  `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...`
- 如果表需要多数据库兼容，不得只更新 `postgresql/` 或只更新某个 DO。
- 已声明 `@KeySequence` 的实体，不得假定只跑在 MySQL 自增模式。

### 4. Validation & Error Matrix

| 场景 | 校验 | 失败行为 |
|------|------|----------|
| 表或字段无注释 | `COMMENT ON` / 列注释缺失 | 拒绝提交，先补语义说明 |
| 只把现有 `deleted` 改成 `is_deleted` | DO、查询、脚本不一致 | 视为破坏契约，禁止落地 |
| 查询仍使用 `SELECT *` | SQL/Mapper 明确列名 | 拒绝提交，继续改写 |
| 深分页继续使用大 `OFFSET` | 评估 keyset/seek | 标记性能风险，不做静默接受 |
| MPJ 联表主表条件直接使用裸字符串列名 | 统一使用 `mainColumn(column)` 等主表列限定方法 | PostgreSQL 下会因任意关联表同名列报字段不明确 |
| PostgreSQL `jsonb` / 数组查询无索引 | 补 `GIN` 等正确索引 | 视为性能缺陷 |
| 更新脚本与 DO 注解不一致 | `@KeySequence` / `@Version` / 字段名漂移 | 编译前即修正 |
| 事务写在 Mapper 层 | 事务边界必须在 service | 视为分层错误 |

### 5. Good / Base / Bad Cases

#### Good

```sql
create table if not exists report_dashboard (
    id bigint generated by default as identity primary key,
    name varchar(100) not null,
    config jsonb not null,
    creator bigint,
    create_time timestamptz not null default now(),
    updater bigint,
    update_time timestamptz not null default now(),
    deleted boolean not null default false
);

comment on table report_dashboard is '仪表盘定义表';
comment on column report_dashboard.config is '仪表盘运行配置 JSON';

create index if not exists idx_report_dashboard_name on report_dashboard (name);
create index if not exists idx_report_dashboard_config_gin on report_dashboard using gin (config);
```

#### Base

- 单表 CRUD 沿用 `BaseDO + BaseMapperX + LambdaQueryWrapperX`。
- 已存在的多数据库模块继续维护 `sql/<vendor>/` 脚本和 `@KeySequence`。
- 默认查询显式过滤软删除字段。

#### Bad

```sql
create table report_dashboard (
    id serial,
    config text,
    is_deleted boolean
);

select * from report_dashboard order by id desc limit 20 offset 200000;
```

### 6. Tests Required

- 脚本一致性检查：
  对受影响模块检查 `mom/sql/**` 和 DO 注解是否同步。
- SQL 静态检查：
  `rg -n "SELECT \\*" mom -g "*.xml" -g "*.java" -g "*.sql"`
- 编译检查：
  `mvn -pl <affected-module> -am -DskipTests compile`
- 性能校验：
  对新增复杂 SQL 至少保留一次 `EXPLAIN` 或等价执行计划结论。
- 软删除校验：
  断言列表/详情查询没有漏掉 `deleted = false` 的默认语义。

### 7. Wrong vs Correct

#### Wrong

```java
@Select("SELECT * FROM report_dashboard ORDER BY create_time DESC LIMIT #{pageSize} OFFSET #{offset}")
List<ReportDashboardDO> selectPage(long offset, int pageSize);
```

#### Correct

```java
default PageResult<ReportDashboardDO> selectPage(ReportDashboardPageReqVO reqVO) {
    return selectPage(reqVO, new LambdaQueryWrapperX<ReportDashboardDO>()
            .likeIfPresent(ReportDashboardDO::getName, reqVO.getName())
            .eq(ReportDashboardDO::getDeleted, Boolean.FALSE)
            .orderByDesc(ReportDashboardDO::getCreateTime));
}
```

#### MPJ Wrong

```java
wrapperX.between("create_time", reqVO.getCreateTime()[0], reqVO.getCreateTime()[1]);
wrapperX.orderByDesc("id");
```

#### MPJ Correct

```java
String MAIN_TABLE_ALIAS = "t";

default String mainColumn(String column) {
    return MAIN_TABLE_ALIAS + "." + column;
}

wrapperX.between(mainColumn(COLUMN_CREATE_TIME), reqVO.getCreateTime()[0], reqVO.getCreateTime()[1]);
wrapperX.orderByDesc(mainColumn(COLUMN_ID));
```

## Scenario: WMS 批次复用回退允许跨物料共用 batchId

### 1. Scope / Trigger

- Trigger: 修改 WMS `transaction_batch` 创建前复用查询、库存初始化批次预取、或任何 `batchId` 跨请求复用 SQL。
- 风险点：标准业务生产线空值没有参与匹配，会把空产线请求误命中非空产线批次；或再次引入其它事实源，导致批次复用口径漂移。

### 2. Signatures

- 标准业务复用键：`itemCode + produceDate + supplierCode + productionLineCode`
- 库存初始化复用键：`itemCode + produceDate + supplierCode`
- 查询事实源：
  `transaction_balance_batch_view`
  `transaction_batch`

### 3. Contracts

- `transaction_balance_batch_view` 命中时可直接按复用键返回 `MIN(batch_id)`。
- 最新业务允许同一个 `batchId` 被多个物料使用，因此余额视图未命中后允许从 `transaction_batch` 反查。
- 标准业务回退维度为生产日期、供应商、生产线；生产线为空时，SQL 必须使用 `COALESCE(production_line_code, '') = COALESCE(#{productionLineCode}, '')` 精确匹配空产线。
- 库存初始化回退维度为生产日期、供应商，不按生产线过滤；新建批次不写入生产线。
- 日期匹配按生产日期自然日归一，SQL 的 `SELECT`、`WHERE`、`GROUP BY` 口径必须一致；保留 `MIN(batch_id)` 作为同组稳定主键选择规则。

### 4. Validation & Error Matrix

| 场景 | 不合格行为 | 合格处理 |
|------|------------|----------|
| 库存初始化 Excel 含 A、B、B，供应商和生产日期相同 | 强制 A、B 拆成不同批次 | A、B、B 允许共用同一个 `batchId` |
| 一般业务余额视图未命中且生产线为空 | 忽略生产线条件，命中非空生产线批次 | 用空生产线作为查询条件，只命中空生产线批次 |
| 日期带时分秒 | `WHERE produce_date::date` 但 `GROUP BY produce_date` | `GROUP BY DATE_TRUNC('day', produce_date)` |

### 5. Good / Base / Bad Cases

- Good: 余额视图未命中后，标准业务查询 `transaction_batch` 的日期、供应商、生产线，并用 `COALESCE` 保留空产线匹配。
- Base: 只从 `transaction_balance_batch_view` 查询，未命中则新建。
- Bad: 标准业务忽略空生产线条件，或视图未命中后绕过 `transaction_batch` 回退规则另查其它事实源。

### 6. Tests Required

- 单元测试：Mock 余额视图未命中，`transaction_batch` 返回同日期、同供应商、同生产线批次，断言不同物料可共用同一 `batchId`。
- 单元测试：Mock 回退结果为非空生产线，断言空生产线请求不得命中。
- SQL 检查：标准业务回退 SQL 必须保留 `COALESCE(tb.production_line_code, '') = COALESCE(#{item.productionLineCode}, '')`。

### 7. Wrong vs Correct

#### Wrong

```sql
select min(tb.id) as batch_id
from transaction_batch tb
where tb.produce_date::date = #{produceDate}::date
  and coalesce(tb.supplier_code, '') = coalesce(#{supplierCode}, '')
group by date_trunc('day', tb.produce_date), tb.supplier_code;
```

#### Correct

```sql
select date_trunc('day', tb.produce_date) as produce_date,
       tb.supplier_code,
       tb.production_line_code,
       min(tb.id) as batch_id
from transaction_batch tb
where tb.deleted = false
  and tb.produce_date::date = #{item.produceDate}::date
  and coalesce(tb.supplier_code, '') = coalesce(#{item.supplierCode}, '')
  and coalesce(tb.production_line_code, '') = coalesce(#{item.productionLineCode}, '')
group by date_trunc('day', tb.produce_date), tb.supplier_code, tb.production_line_code;
```

```java
// 只处理余额视图未命中的键；标准业务即使产线为空，也用空产线参与回退匹配。
fillReusableFromTransactionBatch(resultMap, queryableKeys, inventoryInit);
```
