# Comment Guidelines

> 后端代码注释规范：让读者快速理解业务意图和关键决策。

---

## 注释哲学：Why > What > How

注释的核心价值是降低读者的**理解重建成本**。优先级：

| 优先级 | 内容 | 说明 |
|--------|------|------|
| **最高：Why** | 为什么这样做 | 业务规则、设计决策、约束原因 |
| **中等：What** | 做了什么（非显而易见的） | 状态变迁、副作用、边界条件 |
| **最低：How** | 怎么做的 | 仅当算法或实现方式不直观时 |

**核心原则**：如果代码本身已经清晰表达了 What 和 How，注释只需要解释 Why。

---

## 语言和格式统一

- 注释语言**必须使用简体中文**，包括 Javadoc、Docstring、内联注释、SQL 注释和配置注释。
- 修改代码时只处理本轮新增或本轮触碰逻辑必须同步更新的注释；禁止为了统一风格批量改写既有注释。
- Javadoc 标签使用标准小写格式：`@param`、`@return`、`@throws`。
- **禁止** `@Author`、`@Description`、`@Date` 等非标准标签。
- **禁止** 在注释中用日期标记变更（如 `// 20240715 修改了xxx`），变更历史由 Git 管理。
- **禁止** 保留注释掉的代码块，删除后通过 Git 历史回溯。

## 哪里需要注释

### 必须注释

| 位置 | 触发条件 | 注释内容 |
|------|----------|----------|
| **类级别** | 拥有编排入口、状态机、适配器边界、安全桥接、跨模块契约 | 类的职责边界和行为范围 |
| **公开 API 方法** | 行为非平凡，调用方需要理解前置条件、副作用或返回值语义 | 方法契约 |
| **关键代码块** | 事务、重试、远程协调、令牌校验、缓存变更、事件发布 | 操作顺序和失败后果 |
| **分支和守卫** | 保护不变量、阻止非法状态转换、保留故障状态 | 分支存在的原因 |
| **方法内业务逻辑** | 聚合/混排/窗口计算、降级与空态区分、契约占位或「易误判为 bug」的实现 | 该段逻辑背后的规则、与契约或产品语义的对齐点（Why） |

### 业务逻辑内联注释

**要求**：仅有类/方法级 Javadoc **不够**。凡属**读懂成本高**或与**接口契约 / 产品语义**强相关的实现细节，必须在**方法体内**用内联注释写清「为什么」，避免维护者只读到签名却误判行为。

**典型触发**（出现即应补充内联注释，密度参见下文「状态感知的注释密度」）：

- **聚合与归并**：多来源累加、`total` 与列表长度不一致、按 key merge 的前提（为何可加总、何时不能混用）。
- **降级与空态**：`catch` 后静默跳过 vs 写入 `degradedSources` vs 直接返回空列表且**不**表示 RPC 失败——须注释区分，防止 UI 把降级当成「真实零条」。
- **算法或窗口**：混排、先拉「前 N 条」再内存分页、与单来源直转路径的差异及原因。
- **契约特例**：占位 id、空 `payload` 仍返回成功、错误码区分（`not_supported` vs `not_implemented` vs `failed`）的业务含义。
- **同条件不同语义**：不同入口复用同一批业务条件，但执行目的、结果形态或副作用不同；注释应解释语义差异，代码结构仍要用独立入口表达边界，不能靠注释掩盖含义不清的实现。

**坏示例**（复述步骤，无信息增量）：

```java
// 遍历 provider 并累加
for (WorkbenchProviderClient p : providers) {
    total += p.load();
}
```

**好示例**（点明契约或易错点）：

```java
// 各来源 PageResult.total 为各自查询条件下的全量条数，此处累加作合并视图的规模上界；
// 与 merged 列表物理长度无相等关系，勿当 bug 修改。
for (WorkbenchProviderClient provider : providers) {
    PageResult<Item> page = provider.getPage(req);
    total += defaultLong(page.getTotal());
}
```

```java
// 该入口只复用候选范围，后续处理语义由当前流程单独定义，避免调用方误认为它与另一路径完全等价。
buildCandidateScope(reqVO);
```

### 高价值注释区域（本项目）

- `win-gateway` 的安全过滤器
- 设置 Cookie、Header 或响应封装的 Controller 端点
- 写入或远程调用前做状态校验的 Service 方法
- 行级失败后继续处理的导入/批处理流程

### 不需要注释

- getter/setter、简单 CRUD、框架注解的直接映射
- 从方法名和参数名就能完全理解的逻辑
- 纯数据传输对象（DO/DTO）的字段，除非字段有特殊业务含义

## 注释内容规则

### 好注释回答这些问题

- 为什么这个守卫要提前返回？**背后的业务规则是什么？**
- 失败时哪些状态必须保持不变？**为什么不能回滚？**
- 为什么持久化必须在事件发布之前？**乱序会导致什么后果？**
- 这段代码在重试场景下会不会重复执行？**幂等性如何保证？**

### 坏注释的特征

- 复述代码本身：`// 设置变量`、`// 调用服务`、`// 处理逻辑`、`// 校验参数`
- 复述方法名：`// 创建用户` 写在 `createUser()` 上方
- 空洞的 @param：`@param id` 不加任何描述
- 被注释掉的旧代码或调试代码

### Before / After 对比

**坏：复述代码**

```java
// 根据ID查询用户
User user = userMapper.selectById(id);
// 判断用户是否为空
if (user == null) {
    throw new NotFoundException("用户不存在");
}
```

**好：解释业务规则**

```java
// 跨租户查询前必须先确认目标用户存在且属于当前租户，
// 否则后续的权限继承计算会拿到空上下文导致越权。
User user = userMapper.selectById(id);
if (user == null) {
    throw new NotFoundException("用户不存在");
}
```

**坏：空洞的 Javadoc**

```java
/**
 * 处理
 * @param pcode
 * @param businessName
 * @return
 */
public BusinesstypeRespDTO selectDocumentSetting(String pcode, String businessName) {
```

**好：描述契约和约束**

```java
/**
 * 根据单据编码反查关联的业务类型配置。
 *
 * 仅返回启用状态的配置；若未找到匹配项返回 null 而非抛异常，
 * 由调用方决定缺失配置时的降级策略。
 *
 * @param pcode        单据编码，不可为空
 * @param businessName 业务名称，用于在多配置场景下缩小匹配范围
 * @return 匹配的业务类型配置，无匹配时返回 null
 */
public BusinesstypeRespDTO selectDocumentSetting(String pcode, String businessName) {
```

## Javadoc 模板

### 类级别

```java
/**
 * [一句话说明类的核心职责]。
 *
 * [补充说明行为边界、关键约束或与其他类的协作关系（1-2 句）]。
 */
```

实际示例：

```java
/**
 * 负责工作台页面保存态校验、当前用户页面读写与运行时装配。
 *
 * 保存阶段收口 widget 合法性与权限边界，运行阶段再把 BI 解析结果
 * 和快捷应用可访问性补齐到 payload。
 */
@Service
public class DashboardServiceImpl implements DashboardService {
```

### 方法级别

```java
/**
 * [一句话说明方法的业务目的，而非实现步骤]。
 *
 * [可选：补充关键约束、副作用、或调用方需要知道的注意事项]。
 *
 * @param paramName [说明该参数的业务含义和约束，不要只写类型]
 * @return [说明返回值的业务语义，特别是 null/空集合的含义]
 * @throws XxxException [说明什么业务场景下会抛出]
 */
```

**规则**：

- 每个 `@param` 必须有中文描述，禁止留空。如果参数名本身足够清晰且无额外约束，可以省略整个 `@param` 标签。
- `@return` 在返回值语义不明显时必须写明（如 null 代表什么）。
- `@throws` 只在异常有特定业务语义时添加。

### 内联注释

```java
// [一句话说明为什么，而不是做什么]
code();

// [如果需要更多上下文]
//
// [补充细节：顺序依赖、失败后果、并发考量等]
code();
```

## 状态感知的注释密度

根据代码复杂度选择合适的注释密度。

### 判断标准

| 密度 | 适用场景 |
|------|----------|
| **轻量** | 单一状态转换、无并发、失败处理显而易见 |
| **标准** | 2-3 个分支、有持久化顺序依赖或失败保留逻辑 |
| **完整** | 并发控制、多分支恢复、跨服务协调 |

### 轻量

```java
// READY -> RUNNING：前置校验通过后推进，失败保持 READY
```

### 标准

```java
// READY -> RUNNING：前置校验通过后推进
//
// 持久化先于事件发布，保证下游只看到已确认状态。
// 校验失败保持 READY，并记录审计日志供运维排查。
```

### 完整

```java
// State: READY — 上下文已准备完成，等待执行触发
//
// Trigger: 前置校验通过
// Transition: READY -> RUNNING，持久化后发布流程开始事件
// Failure: 校验失败保持 READY，写入审计日志但不触发告警
// Boundary: 分布式锁防止并发触发导致重复执行
```

仅在分支数、副作用或并发规则确实需要时才升级密度。

## 分层注释指南

### Controller 层

注释重点：**端点的外部可见行为**。

```java
/**
 * 完成 OAuth 回调并在响应中设置 HttpOnly 刷新令牌 Cookie。
 *
 * Cookie 的 Path 限定为 /api/auth，避免被非认证接口的 JS 读取。
 * 认证失败时重定向到登录页而非返回 JSON 错误体。
 */
@PostMapping("/oauth/callback")
public void handleOAuthCallback(...) {
```

不需要注释的 Controller 方法：标准 CRUD 端点、纯转发到 Service 层的薄方法。

### Service 层

注释重点：**校验门控、持久化顺序、重试规则、外部协调**，以及**非平凡分支内的业务规则**（见上文「业务逻辑内联注释」）。

```java
// 保存态先按当前账号权限和后端白名单校验整页配置，
// 拒绝把非法目标持久化进 specJson。
validateWidgetPermissions(pageSpec, currentUser);

// contextKey 必须由后端声明，避免前端保存运行时永远无法解析的自造变量。
assertContextKeysRegistered(pageSpec.getContextBindings());
```

### Mapper / DO 层

通常不需要注释。仅当字段有**隐含的业务规则**时添加：

```java
/**
 * 库存状态码。与 WMS 系统约定：
 * "OK" = 合格品，"HOLD" = 待检品，"SCRAP" = 报废品。
 * 不可自定义扩展，变更需同步 WMS 配置。
 */
private String inventoryStatus;
```

### Gateway / 安全代码

**必须注释**：信任边界、Header 剥离规则、令牌校验逻辑、故意不转发的内容。

```java
// 从上游请求中剥离 X-Internal-* 系列 Header，
// 防止外部请求伪造内部服务间的身份标识。
// 内部 Header 仅在网关鉴权通过后由网关自身注入。
stripInternalHeaders(request);
```

## 区域分隔注释

本项目使用 `// ========== XXX ==========` 风格分隔逻辑区域，保留此风格但需遵守：

- 仅用于常量分组、接口方法分组等**同级元素的逻辑分区**。
- 分隔线内的文字要说明**这组元素的共同特征**，而非重复类名。
- 不要在方法内部使用分隔线，方法内用空行和简短注释分段。

```java
// ========== 客户端错误码（4xx 对应） ==========
ErrorCode BAD_REQUEST = new ErrorCode(400, "请求参数不正确");
ErrorCode UNAUTHORIZED = new ErrorCode(401, "账号未登录");

// ========== 服务端错误码（5xx 对应） ==========
ErrorCode INTERNAL_SERVER_ERROR = new ErrorCode(500, "系统异常");
```

## 禁止模式

| 模式 | 说明 | 替代方案 |
|------|------|----------|
| 注释掉的代码 | `/* old code */` 或 `// oldMethod()` | 直接删除，用 Git 历史回溯 |
| 日期变更标记 | `// 20240715 修改了XXX` | 删除，由 Git commit message 承载 |
| 非标准 Javadoc 标签 | `@Author`、`@Description`、`@Date` | 使用标准 `@author`（仅在团队要求时） |
| 空 @param | `@param id` 无描述 | 要么写清楚描述，要么省略整个标签 |
| 复述代码的注释 | `// 获取用户列表` 在 `getUserList()` 上 | 删除，方法名已经说明了 |
| 业务编号注释 | `// DBT3` 作为唯一说明 | 用业务语言解释，可在末尾附注编号 |
| TODO 无负责人 | `// TODO 修复这个` | `// TODO(zyb): 描述问题和计划` |

## 审查清单

写完注释后用这些问题自检：

- [ ] 本轮新增自定义方法的每个新增调用点上方，是否都有单行中文注释说明调用目的？
- [ ] 注释是否解释了仅靠命名和结构无法理解的内容？
- [ ] **方法体内**：聚合、降级、混排、契约特例等非直观逻辑是否有点明「为什么」，避免只依赖类/方法 Javadoc？
- [ ] 对于工作流代码，注释是否说明了当前状态和允许的下一个状态？
- [ ] 对于失败路径，注释是否说明了是保持、重试、补偿还是放弃当前状态？
- [ ] 注释是否与实际的持久化顺序、发布顺序和远程副作用一致？
- [ ] 每个 `@param` 是否都有实际描述（或在参数名足够清晰时省略了整个标签）？
- [ ] 是否删除了所有注释掉的旧代码和日期变更标记？
