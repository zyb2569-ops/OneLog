# 执行质量思维指南

> **目的**：在动手前判断这次改动应该做局部修复还是结构性修复，并提前定义验证证据。

---

## 核心原则

任务完成不是“代码改完”，而是：根因被处理、失败路径可见、验证证据足够支撑结论。

如果问题触及共享校验、权限、路由、缓存、API 契约、数据库字段、跨模块行为、重复业务逻辑或隐藏兜底，就不能按局部热修处理。先找应该成立的不变量，再让代码在一个地方表达这个不变量。

---

## 动手前判断

### 第一步：区分局部修复和结构性修复

| 触发点 | 判断 |
|--------|------|
| 只改一个展示文案、字段标题、样式细节 | 可局部修复 |
| 涉及多个入口、多个页面、多个模块或多张表 | 倾向结构性修复 |
| 发现同一逻辑有多个实现 | 结构性修复 |
| 需要新增 fallback 才能“跑通” | 先重新追根因 |
| 涉及权限、数据完整性、安全边界 | 结构性修复 |

### 第二步：先定义失败如何暴露

修复前必须回答：

- 当前失败是异常、错误码、日志、空结果、错数据，还是页面状态异常？
- 失败应该在入口层暴露，还是在业务层暴露？
- 是否存在吞异常、空 catch、默认值兜底、mock 成功路径？
- 修复后如何证明失败路径仍然可见？

### 第三步：定义验证顺序

验证应从最靠近改动的证据开始，再扩大范围：

1. 目标行为测试或脚本。
2. 类型检查、编译或 lint。
3. 受影响模块构建。
4. 最小真实链路 smoke test。

如果某一步不能执行，必须记录原因和替代证据，不能把“未验证”写成“通过”。

---

## 常见错误

### 错误 1：用兜底隐藏坏数据

坏做法：

```
上游字段为空 → 下游随便给默认值 → 页面不报错
```

正确做法：

```
上游字段为空 → 追到第一个丢字段的位置 → 修复写入或转换契约 → 用失败样本复验
```

### 错误 2：把验证命令当作形式

运行服务、启动页面或看到接口返回 200，都不是充分证据。必须检查目标字段、目标状态或目标副作用是否符合预期。

### 错误 3：修同一处三次仍按原思路推进

连续失败说明当前假设不可靠。此时应增加可观察证据，例如运行时日志、数据库对比、请求/响应快照或浏览器运行态测量，然后换路径追根因。

---

## 检查清单

动手前：

- [ ] 已判断这是局部修复还是结构性修复。
- [ ] 已找出本次改动必须维护的不变量。
- [ ] 已确认不会新增隐藏 fallback、mock 成功路径或吞异常逻辑。
- [ ] 已定义最小验证证据。

完成前：

- [ ] 已按目标测试、静态检查、构建、smoke test 的顺序验证可执行项。
- [ ] 已检查 diff 中是否出现重复逻辑、第二事实源、宽泛 catch、无关格式化或未说明的行为变化。
- [ ] 如果无法运行验证，已写清楚原因和替代检查。
