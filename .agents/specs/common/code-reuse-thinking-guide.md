# 代码复用思维指南

> **目的**：写新代码前先想清楚——它是不是已经存在了？

---

## 问题所在

**重复代码是不一致性 bug 的头号来源。**

当你复制粘贴或重新实现已有逻辑时：
- bug 修复无法自动传播到所有副本
- 各处行为会随着时间推移逐渐产生分歧
- 代码库越来越难以理解和维护

---

## 写新代码之前

### 第一步：先搜索

```bash
# 搜索相似的函数名
rg "functionName"

# 搜索相似的逻辑
rg "keyword"
```

### 第二步：问自己这些问题

| 问题 | 如果是的话 |
|------|------------|
| 是否已经存在类似函数？ | 直接使用或扩展它 |
| 这个模式是否在其他地方用过？ | 遵循已有模式 |
| 这段逻辑能否提取为共享工具？ | 在合适的位置创建它 |
| 我是否在从另一个文件复制代码？ | **停下来**——提取到共享位置 |

---

## 常见重复模式

### 模式 1：复制粘贴函数

**坏做法**：把一个校验函数复制到另一个文件

**好做法**：提取到共享工具模块，在需要的地方导入

### 模式 2：相似组件

**坏做法**：新建一个与已有组件 80% 相似的组件

**好做法**：通过 props/variants 扩展已有组件

### 模式 3：重复常量

**坏做法**：在多个文件中定义相同常量

**好做法**：单一数据源定义，其他地方导入

## 什么时候该抽象

**应该抽象的场景**：
- 相同代码出现 3 次以上
- 逻辑复杂到容易出 bug
- 多人可能需要复用这段逻辑

**不该抽象的场景**：
- 只使用了一次
- 非常简单的单行代码
- 抽象本身比重复代码更复杂

**后端 Service / 前端 composable 专项**：已有 util、Support、Api 时禁止再包薄转发；单调用单行转发应内联。详见 [方法抽象边界](./private-method-abstraction-guidelines.md)。

---

## 批量修改后

当你对多个文件做了类似修改后：

1. **回顾**：是否遗漏了某些实例？
2. **搜索**：用 `rg` 检查是否有漏网之鱼
3. **考虑**：是否应该提取为共享代码？

---

## 陷阱：不同机制产生相同输出

**问题**：当两种不同机制必须产生相同的文件集（例如初始化时递归复制目录，而更新时手动 `files.set()`），结构变更（重命名、移动、添加子目录）只会通过自动机制传播，手动维护的那条路径会悄悄地与实际结构产生偏差。

**症状**：初始化时完美运行，但更新时文件路径错误或文件缺失。

**预防清单**：
- [ ] 迁移目录结构时，搜索所有引用旧结构的代码路径
- [ ] 如果一条路径是自动派生的（glob/copy），另一条是手动列出的，手动那条必须同步更新
- [ ] 添加回归测试，比较两种机制的输出是否一致

## 提交前检查清单

- [ ] 已搜索过类似的现有代码
- [ ] 没有应该共享却被复制粘贴的逻辑
- [ ] 常量只在一个地方定义
- [ ] 相似模式遵循相同的结构
