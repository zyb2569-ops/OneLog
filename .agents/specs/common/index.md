# 思维指南

> **目的**：拓展思考维度，帮助你发现可能遗漏的问题。

---

## 为什么需要思维指南？

**大多数 bug 和技术债源于"没想到"**，而非能力不足：

- 没想到跨层边界会发生什么 → 跨层 bug
- 没想到代码模式在重复 → 到处都是重复代码
- 没想到边界情况 → 运行时错误
- 没想到未来维护者的感受 → 难以阅读的代码

这些指南帮助你**在编码前问对的问题**。

## 快速参考：思维触发点

### 什么时候需要考虑跨层问题

- [ ] 功能涉及 3 个以上层（API、Service、Component、Database）
- [ ] 数据格式在层间发生变化
- [ ] 多个消费方需要相同数据
- [ ] 不确定某些逻辑应该放在哪一层

→ 阅读 [跨层思维指南](./cross-layer-thinking-guide.md)

### 什么时候需要根因优先

- [ ] 用户描述的是“某处不显示、某处为空、某结果不对”
- [ ] 字段经过多层复制、转换、派生或展示
- [ ] 下游可以通过回查源数据补值，但还没解释为什么上游为空
- [ ] 已经准备在现象发生处打补丁

→ 阅读 [根因优先思维指南](./root-cause-thinking-guide.md)

### 什么时候需要考虑代码复用

- [ ] 正在写的代码和已有代码相似
- [ ] 看到同一模式重复 3 次以上
- [ ] 正在往多个地方添加新字段
- [ ] **正在修改任何常量或配置**
- [ ] **正在创建新的工具/辅助函数** ← 先搜索是否已存在！
- [ ] **正在新增 private 方法或 validator 转发** ← 先读方法抽象边界！

→ 阅读 [代码复用思维指南](./code-reuse-thinking-guide.md)、[方法抽象边界](./private-method-abstraction-guidelines.md)

### 什么时候需要执行质量收口

- [ ] 改动涉及共享校验、权限、路由、缓存、API 契约或数据库字段
- [ ] 需要新增 fallback、默认值或异常捕获才能让流程继续
- [ ] 同一个问题已经修过但仍复现
- [ ] 准备报告完成，但还没有可复现的验证证据

→ 阅读 [执行质量思维指南](./execution-quality-thinking-guide.md)

## 修改前必查规则（关键）

> **修改任何值之前，务必先搜索！**

```bash
# 搜索你即将修改的值
rg "value_to_change"
```

仅这一个习惯就能防止大多数"忘了更新 X"的 bug。

## 如何使用本目录

2. **编码中**：感觉重复或复杂时，查阅指南
3. **修 bug 后**：将新发现补充到相关指南中（从错误中学习）
