# 根因优先思维指南

> **目的**：避免只修用户描述的表象，确保问题被追到第一个错误发生点。

---

## 核心原则

用户描述的是症状，不一定是根因。

当问题表现为“下游展示为空、结果不对、某一步缺字段”时，不能默认在下游补值或兜底。先沿数据流向上追溯，找到最早应该产生该数据的位置，并确认那里为什么没有写对。

---

## 调试顺序

### 第一步：把症状改写成数据问题

不要停留在页面现象或接口现象上，要写成可验证的数据断言：

- 哪个字段为空？
- 哪张表、哪个接口、哪个对象为空？
- 是所有数据为空，还是某条路径为空？
- 旧数据和新数据是否表现一致？

### 第二步：画出数据来源链路

按实际流转画链路：

```
输入 / 原始来源 → 中间对象 → 持久化表 → 派生对象 → 查询接口 → 前端展示
```

每一段都要回答：

- 该字段应该由谁生成？
- 是否只是复制上游字段？
- 如果上游为空，下游是否有资格重新计算？
- 哪一步是第一个把正确值变成空值或错误值的地方？

### 第三步：先查第一个错误写入点

如果派生表、记录表、展示表字段为空，优先检查它依赖的源表或源对象是否已经为空。

不要把“在下游回查源数据再补回来”当成首选修复；这通常只是掩盖了上游写入、转换或校验漏掉字段的问题。

### 第四步：只在确认根因后修复

修复位置应靠近根因：

- 上游写入漏字段 → 修上游写入。
- 转换丢字段 → 修转换契约。
- 保存前对象被覆盖 → 修覆盖点。
- 下游展示字段不一致 → 修前后端契约。

只有在业务明确允许下游重算时，才在下游补值，并写清楚它是业务规则，不是调试捷径。

---

## 常见错误

### 错误 1：用户说哪里不显示，就只修哪里

症状在前端，不代表根因在前端。

症状在记录表，不代表记录生成处就是根因。记录表可能只是复制了申请、任务或库存包装等上游对象的空值。

### 错误 2：用回查兜底替代根因修复

坏做法：

```
记录表缺字段 → 生成记录时再查一遍源表补上
```

正确做法：

```
记录表缺字段 → 查记录从哪来 → 查源对象为何为空 → 修第一个漏写/漏转位置
```

### 错误 3：只看代码，不看真实数据

代码路径判断必须用真实数据校验：

- 查实际数据库，不用过期 SQL 文件当事实。
- 查最新出问题的数据行。
- 对比源表和派生表同一业务单号的字段。
- 用数据证明是哪条路径出错。

---

## 检查清单

修 bug 前：

- [ ] 已把用户描述改写成具体字段、表、接口或对象的断言。
- [ ] 已查真实运行环境或当前激活数据库的数据，而不是只看旧脚本。
- [ ] 已画出该字段从源头到展示的完整链路。
- [ ] 已确认上游源数据是否正确。
- [ ] 已找到第一个错误写入、错误转换或错误覆盖的位置。
- [ ] 修复点靠近根因，而不是在下游兜底补值。

修 bug 后：

- [ ] 已验证同一业务单号在源表、中间表、目标表之间字段一致。
- [ ] 已覆盖至少一条曾经失败的真实路径。
- [ ] 如果保留了下游兜底，已说明它的业务原因和边界。
