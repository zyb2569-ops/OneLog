# Comment Guidelines

> 前端代码注释规范：让读者快速理解 UI 状态流转和关键决策。

---

## 注释哲学：Why > What > How

注释的核心价值是降低读者的**理解重建成本**。优先级：

| 优先级 | 内容 | 说明 |
|--------|------|------|
| **最高：Why** | 为什么这样做 | 业务规则、设计决策、约束原因 |
| **中等：What** | 做了什么（非显而易见的） | 状态变迁、副作用、边界条件 |
| **最低：How** | 怎么做的 | 仅当算法或实现方式不直观时 |

**核心原则**：如果代码本身已经清晰表达了 What 和 How，注释只需要解释 Why。

---

## 语言和格式统一

- 注释语言**必须使用简体中文**，包括 Vue 模板注释、JSDoc、TypeScript 内联注释和配置注释。
- JSDoc 标签使用标准格式：`@param`、`@returns`、`@throws`。
- TypeScript 代码中 `@param` **不写类型**（类型由 TS 签名提供），只写业务含义。
- **禁止** 保留注释掉的代码（包括 `console.log` 调试语句），通过 Git 历史回溯。
- **禁止** 在注释中用日期标记变更，变更历史由 Git 管理。

## 哪里需要注释

### 必须注释

| 位置 | 触发条件 | 注释内容 |
|------|----------|----------|
| **文件/组件级别** | 拥有状态机、迁移适配器、跨层契约、路由级编排角色 | 组件的职责和生命周期要点 |
| **公共/共享工具函数** | 被多文件复用且签名不足以说明契约 | 函数契约和边界情况 |
| **关键代码块** | 认证引导、存储迁移、异步排序、渲染门控、降级行为 | 操作顺序和失败后果 |
| **分支和守卫** | 阻止无效渲染、保护 UI 状态、拦截不安全导航 | 分支存在的原因 |
| **组件内业务逻辑** | 与后端契约绑定的展示策略、列表/角标与降级字段的联动、多步异步的先后依赖 | 为何该分支这样渲染或请求，错误时用户可见结果是什么 |

### 业务逻辑内联注释

**要求**：仅有文件/函数顶部的说明**不够**。凡依赖**接口字段语义**（例如 `degradedSources` 与空列表的区别）、**多请求编排**或**易误判为 UI bug** 的分支，必须在**关键代码旁**用简短注释写清「为什么」，避免只写 props/类型而读者仍踩坑。

**典型触发**：

- **降级与空态**：`degradedSources.length > 0` 时不得把列表空当成「无数据」；须注释与文案/占位策略的对应关系。
- **角标与列表**：汇总接口与列表接口字段分工（如未读数来自 `summary` 而非当前页 `list.length`）。
- **异步顺序**：先拉 A 再拉 B 的原因；过时响应丢弃或竞态防护。

**坏**：`// 调接口`  
**好**：说明该请求失败时保留何种 UI 状态、是否与契约中的降级字段一致。

### 高价值注释区域（本项目）

- axios 拦截器和 token 刷新路径
- 存储层（storage）的数据规范化和兼容性迁移
- 运行时 widget 的多步加载和引导行为
- 路由守卫和权限驱动的 UI 降级

### 不需要注释

- 简单的 ref/reactive 声明、标准 computed、直白的 watcher
- 模板中的结构性代码（v-for、v-if 对应简单条件）
- 标准 CRUD 组件中无特殊逻辑的 props 传递

## 注释内容规则

### 好注释回答这些问题

- 为什么这个渲染分支还不能进入？**阻塞条件的业务原因是什么？**
- 请求失败时哪些 UI 状态需要保持？**为什么不能重置？**
- 为什么这个异步步骤必须在另一个之前执行？**乱序会导致什么用户可见问题？**
- 这个操作完成后浏览器会产生什么可见副作用？**用户会看到什么变化？**

### 坏注释的特征

- 复述代码本身：`// 设置 loading 为 true`、`// 监听 props 变化`、`// 调用 api`
- 逐行翻译 Vue 语法：`// 遍历列表`、`// 条件渲染`
- 空洞的 props 注释：`// 是否显示` 写在 `visible` 上
- 被注释掉的 `console.log` 或调试代码

### Before / After 对比

**坏：逐行翻译代码**

```ts
// 设置loading
const loading = ref(true)
// 获取数据
const data = await fetchData()
// 关闭loading
loading.value = false
```

**好：解释决策和后果**

```ts
// 先展示骨架屏再请求数据，避免空白页面闪烁。
// 请求失败时保持骨架屏并显示重试按钮，而非切换到空状态。
const loading = ref(true)
const data = await fetchData()
loading.value = false
```

**坏：无信息量的 props 注释**

```ts
// 是否多选
selection: propTypes.bool.def(false),
// 是否显示
visible: propTypes.bool.def(true),
```

**好：解释 props 的业务含义和约束**

```ts
// 开启多选时 Table 左侧显示 checkbox 列，选中行数据通过 selection-change 事件抛出。
// 与 multiple 配合：selection=true + multiple=false 表示单选模式（radio 样式）。
selection: propTypes.bool.def(false),
```

**规则**：简单且命名清晰的 props（如 `disabled`、`placeholder`）不需要注释。只在 props 之间有联动关系、默认值有业务含义、或命名无法完全表达行为时才注释。

## JSDoc 模板

### 组件级别

```vue
<!--
  [一句话说明组件的核心职责]。

  [补充说明：关键的状态流转、与父组件的通信契约、或需要注意的生命周期行为]。
-->
```

### 工具函数

```ts
/**
 * [一句话说明函数的业务目的]。
 *
 * [可选：补充边界情况、返回值特殊语义、调用方需要注意的约束]。
 *
 * @param paramName [业务含义和约束，不写类型]
 * @returns [返回值的业务语义，特别说明 null/空数组/undefined 的含义]
 */
```

实际示例：

```ts
/**
 * 将扁平列表按 parentId 关系组装为树结构。
 *
 * 无父节点的项（parentId 为 0 或空）自动归入根层级。
 * 返回的树保留原始引用，修改节点属性会影响源数据。
 *
 * @param list 含 id 和 parentId 字段的扁平数据
 * @param rootValue 根节点的 parentId 判定值，默认为 0
 * @returns 树形结构数组，无匹配数据时返回空数组
 */
export const listToTree = <T extends TreeNode>(list: T[], rootValue = 0): T[] => {
```

**规则**：

- `@param` 不写 `{Type}`，TypeScript 签名已提供类型信息。
- 每个 `@param` 必须有中文描述，否则省略整个标签。
- `@returns` 在返回值语义不明显时必须写明。

### 内联注释

```ts
// [一句话说明为什么，而不是做什么]
code()

// [如果需要更多上下文]
//
// [补充细节：顺序依赖、失败后果、竞态考量等]
code()
```

## 状态感知的注释密度

根据 UI 流程复杂度选择合适的注释密度。

### 判断标准

| 密度 | 适用场景 |
|------|----------|
| **轻量** | 单一状态转换、无竞态、失败处理显而易见 |
| **标准** | 2-3 个分支、有异步顺序依赖或失败保留逻辑 |
| **完整** | 竞态控制、多分支恢复、跨组件状态协调 |

### 轻量

```ts
// idle -> ready：依赖加载完成后才允许展示主视图
```

### 标准

```ts
// idle -> loading -> ready：所有前置请求完成后才进入可交互态
//
// 加载失败时保持降级界面，不暴露半完成状态。
// 用户只会看到「加载中」或「完整可操作」两种状态。
```

### 完整

```ts
// State: prepared — 基础数据已就绪，但主视图还未满足展示条件
//
// Trigger: 所有前置请求完成且结果仍属于当前页面上下文
// Transition: prepared -> rendering -> ready
// Failure: 保持 blocked UI，展示可重试提示
// Boundary: 请求序号校验避免旧响应覆盖新状态（路由快速切换场景）
```

仅在核心 UI 生命周期节点、竞态守卫或多分支恢复逻辑时才使用完整密度。

## 分层注释指南

### Vue 组件

注释重点：**渲染门控、降级 UI、异步排序**，而非模板结构。

```vue
<script setup lang="ts">
// 初始化完成前阻止主视图渲染，避免首次渲染暴露不完整的数据状态。
// 初始化失败时保持 fallback UI 而非切换到空白的交互界面。
const initialized = ref(false)
</script>
```

不需要注释的组件代码：标准的 `v-for` 渲染列表、简单的表单双向绑定、纯展示性 computed。

### Composable / Hook

注释重点：**共享契约、变更顺序、兼容行为**。

```ts
/**
 * 管理可分页列表的加载状态和数据获取。
 *
 * 页码变更时自动取消前次未完成的请求，避免旧数据覆盖新结果。
 * 组件卸载时自动清理进行中的请求。
 */
export function usePagedList<T>(fetcher: PageFetcher<T>) {
```

### Watcher 和 Computed

仅在依赖关系微妙或需要防止过时异步结果时注释：

```ts
// 仅在 formData 和 permission 都就绪后才计算可见字段，
// 避免权限数据未到位时渲染出完整表单后又闪烁隐藏。
const visibleFields = computed(() => {
  if (!permission.value) return []
  return formData.value.fields.filter(f => permission.value.canView(f.key))
})
```

### API 封装

通常不需要注释。仅在端点有**非常规的浏览器或认证副作用**时添加：

```ts
/**
 * 调用登出接口并清除本地 token。
 *
 * 注意：接口返回前会先清除本地状态，确保即使请求超时也不会残留登录态。
 * 响应后重定向到登录页，不使用 router.push 以强制刷新全局状态。
 */
export function logout() {
```

## 禁止模式

| 模式 | 说明 | 替代方案 |
|------|------|----------|
| 注释掉的代码 | `// oldMethod()` 或 `/* old block */` | 直接删除，用 Git 历史回溯 |
| 注释掉的 console.log | `// console.log('debug', data)` | 直接删除 |
| 日期变更标记 | `// 20240715 修改了XXX` | 删除，由 Git commit message 承载 |
| 带类型的 @param | `@param {string} name` | 省略 `{string}`，TS 签名已有类型 |
| 空 @param | `@param name` 无描述 | 要么写清楚描述，要么省略整个标签 |
| 复述代码的注释 | `// 设置 loading 为 true` | 删除 |
| 逐个 props 注释 | 每个 prop 上方都写 `// 是否xxx` | 仅在有联动关系或默认值有业务含义时注释 |
| TODO 无负责人 | `// TODO 修复这个` | `// TODO(zyb): 描述问题和计划` |

## 审查清单

写完注释后用这些问题自检：

- [ ] 注释是否解释了仅靠阅读多个 reactive 分支才能推断出的内容？
- [ ] **关键分支旁**：与后端契约相关的展示（如 `degradedSources`、角标来源）是否在代码附近点明，避免只依赖文件头注释？
- [ ] 对于异步 UI 流程，注释是否说明了当前状态和允许的下一个状态？
- [ ] 对于失败路径，注释是否说明了 UI 是重试、保持、降级还是放弃当前状态？
- [ ] 注释是否与实际的请求顺序和用户可见结果一致？
- [ ] 每个 `@param` 是否都有实际描述（或在参数名足够清晰时省略了整个标签）？
- [ ] 是否删除了所有注释掉的旧代码和 `console.log`？
- [ ] Props 注释是否只出现在有联动关系或特殊语义的地方，而非逐个标注？
